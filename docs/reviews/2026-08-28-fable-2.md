## P1

### F1. `tail` misses the last output chunk: the bridge sends the end `status` before the `data` that carries it
`packages/bridge/src/bridge.js:95-113` (send order) · `apps/web/src/lib/terminal/adapter.ts:89-102` (finishes on status) — lane C.

`t.onData` runs `osc.feed(data)` first and calls `sendStatus()` on the `end` event **inside the loop**,
then sends the `data` frame *after* the loop. The live adapter finishes the in-flight proposal on the
first `status{running:false}` — before the chunk containing the last lines and `133;D` arrives — so
whatever output shares that chunk is dropped (and the tail carries the echoed command line instead).

Measured (`scratchpad/pty-probe.ts`, zsh, real PTY, N=3): proposal
`echo tail_line_1; echo tail_line_2; echo tail_line_3` → `exit 0`, tail lines containing output:
**2/3, 1/3, 1/3**. `tail=["eecho tail_line_1; …","tail_line_1"]` on run 1.

Fix (either side): bridge — send the `data` frame **before** emitting the `end` status (or buffer the
status until after `send(client,{type:'data'})`); adapter — finish on the `end` event from its own
`PromptDetector` (it already parses `133;D`) and read exit/ms from the *next* status frame. Add a
smoke/terminal case asserting the tail contains every echoed line.

### F2. Enter on a ghost is not gated on the bridge's honest `running` — the proposal goes into the running program's stdin
`apps/web/src/components/Terminal.tsx:143-152` · `apps/web/src/lib/terminal/adapter.ts:169-178` — lane C.

`LineBuffer` resets on the human's Enter, so while their own command runs (`cat`, `vim`, `ssh`,
`python`, `less`) the line is "empty", the ghost is drawn, and Enter sends `command + "\r"` — into that
program. The bridge already knows (`status.running === true`, honest via OSC 133;C); nothing checks it.

Measured (zsh): human types `cat⏎` → `lastStatus.running=true, last_command="cat"` → propose
`echo PROPOSAL_WENT_TO_CAT` → `acceptProposal` → **true**; `cat` echoed the line back; no end marker;
`inFlight` stuck (see F3).

Fix: `acceptProposal` returns false (and `Terminal.tsx` hides the ghost / shows "a command is running")
when `client.lastStatus?.running === true` and `hello.integration`; `terminal_propose` may still
queue, but the ghost is only *offered* at a prompt (`133;A` seen since the last `133;C`).

### F3. Without shell integration the adapter wedges after the first accepted proposal
`apps/web/src/lib/terminal/adapter.ts:172, 85-102` · `Terminal.tsx:150-152` — lane C.

`inflight` clears only on `start` (133;C) → `status{running:false}`. bash/sh/fish emit neither, so the
first accepted proposal stays in flight forever: `acceptProposal` returns **false** for every later
proposal, `Terminal.tsx` ignores the return value **and consumes the key** (`return consume()`), and
`terminal_wait` answers `still_waiting` until the tab dies. Same wedge in zsh after Tab-insert → Ctrl-U
→ Enter (line empty, `insertedId` matches → `acceptProposal(alreadySent)` with nothing sent).

Measured (`--shell /bin/bash`): `hello.integration=false` · accept #1 → true · `waitProposal` 2.5 s →
`null` · `inFlight` still set · accept #2 → **false** (Enter silently swallowed).

Fix: when `hello.integration === false`, resolve at Enter with `exit_code:null, ms:null` (Gate-A
semantics; `measured:false` already says so) and never set `inflight`; with integration on, also
finish `inflight` on the next `prompt` event (133;A) with `exit_code:null`, and let `Terminal.tsx` fall
through (send the key normally) when `acceptProposal` returns false.

### F4. Judge Worker: `/ws/:sid` and `DELETE /api/session/:sid` start a container for any well-formed sid — the Gate is bypassable
`infra/sandbox/src/worker.ts:102-108, 93-100` — lane C.

Both routes call `getSandbox(env.Sandbox, sid)` with no check that the sid was ever issued.
`wsConnect` → `Sandbox.fetch` → `super.fetch` → `containerFetch` → `startAndWaitForPorts` when the
container is not running (SDK: `@cloudflare/containers/dist/lib/container.js:864-870`, read today).
`destroy()` on a fresh id instantiates a DO too. So `GET /ws/<24 random hex>` with upgrade headers spawns
a container (port 7331 never opens → 500 after the wait, but the instance is up until `sleepAfter`,
default 10 m). Ten requests = `max_instances: 10` exhausted = judge mode dead for 10 minutes, no rate
limit involved. Not runtime-reproduced (no Cloudflare login); the SDK code path is deterministic.

Fix (stateless, 10 lines): issue `sid = hex(12) + '.' + HMAC-SHA256(SID_SECRET, hex)[:16]` and verify
before any `getSandbox`; or record issued sids in the Gate DO (it already has the row) and look up by
sid. Also drop the `DELETE` route — nothing in `session.ts` calls it.

### F5. The `LineBuffer` Enter-gate is blind to paste and history recall — SECURITY.md §1 claims more than the mechanism does
`apps/web/src/lib/terminal/linebuffer.ts:39-73` · `components/Terminal.tsx:116-119, 166` — lane C.

`feedText` is called only on Tab-insert; `term.onData` (paste, IME, middle-click) is not counted; ↑/↓/
Ctrl-R/Ctrl-P/Ctrl-N/Alt-. return `false` ("arrows… ignored"). After ⌘V or ↑ the shell line is full,
`lineEmpty` is still true, the ghost is shown, and Enter sends `command + "\r"` **appended to that
line** → the shell runs `<recalled or pasted text><command>`. SECURITY.md §1 row 4 says "Enter never
sends a proposal over partial input". Code path only (not reproduced headlessly — needs a paste event).

Fix: treat the buffer as *dirty* (not empty) on any of ↑ ↓ PageUp Ctrl-R/P/N/Y, Alt-., and on any
`onData` payload > 1 char, until the next `133;A`; with integration off, never trust "empty" after a
non-printable key.

  for each step; the client-forward allowlist (`ws/protocol.ts:24`, `bridge/src/protocol.js:48`) lists
  `executed_step`, which nothing emits, and `ledger.ts:15` has no such kind; `session.ts:93` filters on the
  allowlist, so every forged-step `executed` row stays uncountersigned (no ✓ in the ledger pane). Rename to
  `executed_step` in `forge.ts` + `LedgerKind`, or allowlist `executed` with `origin:'client'`. — lane C
- **F8.** `apps/web/src/lib/ws/client.ts:135-137, 214-217` — the no-hello timer closes with
  `CLOSE_CODES.UNAUTHORIZED`, and `onClosed` maps 4401 to the terminal `unauthorized` state (no retry). A
  cold judge pair slower than 5 s (image hello measured 1079 ms; a cold container can exceed it) shows
  "unauthorized" and never reconnects. Use a private code for the local timeout and keep retrying. — lane C
- **F9.** `docs/SECURITY.md` §4 "Bridge binds loopback only" — judge mode runs `--host 0.0.0.0`
  (`worker.ts:70`); §6 should state it and that only the Worker's `wsConnect` proxy reaches port 7331. — lane C
- **F10.** `infra/sandbox/wrangler.jsonc:25` `SESSIONS_PER_IP_PER_10MIN=1` — two judges (or a judge and
  a colleague) behind one office NAT block each other for 10 min with a 429; the cost of 3/10 min is low

- **F11.** `packages/bridge/src/mcp.js:42-79` — `AgentLink` never reconnects; after a bridge restart the

- **F12.** `components/Terminal.tsx:150-152` — `adapter.acceptProposal(p.id)`'s return value is ignored and
  the key is consumed; when it returns false (in flight, unpaired, F2/F3) the human's Enter does nothing

- **F13.** `apps/web/src/lib/ws/client.ts:163, 251-253` — up to 100 `input` frames typed while
  `connecting` are replayed into the shell after a *re*-pair, against whatever prompt state the shell is

- **F14.** `infra/sandbox/src/worker.ts:93-100` — `DELETE /api/session/:sid` is unauthenticated (sid only)
