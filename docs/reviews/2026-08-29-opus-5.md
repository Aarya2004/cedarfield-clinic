## P0 — 1. `interceptHttps = false` silently removed the egress allowlist for HTTPS.
`infra/sandbox/src/worker.ts:46` (comment at :44–45 asserts the opposite) · commit `29c26a5`

The class sets `enableInternet = false`, `interceptHttps = false`, and a 54-host `allowedHosts`.
The comment on line 44 states: *"`allowedHosts` still filters egress by host (deny-by-default), so
egress stays locked to the demo status/doc hosts below."*

**That is not how the SDK works.** The allowlist gate lives inside `ContainerProxy.fetch`
(`@cloudflare/containers@0.3.7/dist/lib/container.js:209`):

```js
// 2. allowedHosts: when set, acts as a whitelist gate — only matching hosts can proceed.
if (allowedHosts && !matchesHostList(hostname, allowedHosts)) {
    return new Response('Origin is disallowed', { status: 520 });
}
```

That code only ever runs for traffic that was **intercepted and routed through the proxy**. What
gets intercepted is decided in `applyOutboundInterception` (`container.js:1198–1213`):

```js
if (interceptAll) {
    // If HTTPS interception is enabled, intercept all HTTPS traffic too
    if (this.interceptHttps) {
        await this.container.interceptOutboundHttps('*', fetcher);   // <-- SKIPPED
    }
    await this.container.interceptAllOutboundHttp(fetcher);          // <-- HTTP only
}
```

`interceptOutboundHttp*` and `interceptOutboundHttps` are distinct runtime calls, and the SDK's own
doc comment (`container.js:1166`) says HTTPS interception is applied *"when `interceptHttps` is
enabled"*. With it `false`, **HTTPS connections are never intercepted, so they never reach the
`allowedHosts` gate.** The allowlist now governs plain HTTP only — and every one of the 54 hosts is
an HTTPS host, so in practice it governs nothing.

Setting `allowedHosts` does still flip `shouldInterceptAllOutbound()` to true
(`container.js:1124`, via `effectiveAllowedHosts`), which is why HTTP is caught — that is the part
that still works, and it is what makes the misconfiguration hard to see.

**Failure scenario.** A stranger clicks *Try it now*, gets a shell, and runs
`curl -s https://any-host-they-control.example/` — or a reverse shell over HTTPS, or a crypto
miner's HTTPS pool, or exfiltration of anything they can reach. It is not blocked. The container is
handed to anonymous visitors, rate-limited only to 3 per IP per 10 minutes, with a 30-minute TTL.
There is no API key to steal (that part of the design is sound), so the exposure is **outbound
abuse from Cloudflare-hosted infrastructure attributable to this account**, not data theft.

**Evidence the HTTPS path is open rather than merely unfiltered:** `29c26a5`'s own purpose was that
turning interception off is what let rokan-do's HTTPS fetch of `githubstatus.com` succeed
(previously it failed TLS and abstained). A live, working HTTPS fetch that never passes the gate is
exactly the condition above.

**The claim is also undocumented-as-tested and unmeasured:**
- `docs/SECURITY.md:70` — "`enableInternet=false` with an **HTTP/S** allowlist", under
  `SECURITY.md:7` "Everything below is implemented and covered by a test that fails when it
  regresses". No such test exists: `infra/sandbox/test/` is `dockerfile-rokan`, `gate`, `origin`,
  `sid` — I grepped all 15 sandbox tests for `allowedHosts|egress|520` and got **zero** hits.
- `docs/SECURITY.md:85` carefully discloses that raw TCP/UDP is unfiltered but says nothing about
  HTTPS — the reader concludes HTTPS *is* filtered.
- `docs/SUBMISSION.md:54` sells "egress allowlist" in the judged text, to a panel containing
  Cloudflare's own agents/edge lead.
- `docs/FIELD-NOTES.md` has no egress row at all — every other security control in this repo has a
  measured note; this one was never measured.

**I could not execute the confirming test** (no Docker builds, and confirming it live would burn a
judge session slot from the builder's IP). It is 30 seconds in a live sandbox:

```
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/     # allowlisted host → expect 200
curl -s -o /dev/null -w '%{http_code}\n' https://icanhazip.com/   # NOT allowlisted → 520 = gated, 200 = open
```

If the second returns 200, the allowlist is not enforcing HTTPS and the docs must change or the
config must.

**Fix options, in order of preference.** (a) Restore `interceptHttps = true` and solve the rokan-do
TLS failure properly — point Python at the injected CA (`REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE`), since
the SDK already sets `SANDBOX_INTERCEPT_HTTPS=1` for exactly this. (b) Keep interception off and
**delete the allowlist claim** from `SECURITY.md`, `SUBMISSION.md` and the `worker.ts` comment,
replacing it with what is true: "HTTP egress is allowlisted; HTTPS is not filtered; there is no API
key in the container." Option (b) is honest and cheap, but it hands Galloni a worse story than (a).
What is not acceptable is the current state: the strongest security claim in the submission, stated
in a code comment that the SDK contradicts.

## P2 — 2. `runs` is incremented when the agent *calls* a forged tool, not when anything runs — and it survives a re-forge that changes the content hash.
`apps/web/src/lib/webmcp/forge.ts:427` and `:299`

`invoke()` does `t.runs += 1` (line 427) immediately after minting the proposals, **before** the
human has decided anything. Nothing decrements it. `FORGE_LIST_DESCRIPTION`
(`schemas.ts:230`) tells the agent these are *"measured stats: runs, median_ms, last_exit"*.

**Failure scenario A (honesty).** The agent calls `forged_deploy` five times; the human presses Esc
every time. `forge_list` reports `runs: 5, median_ms: null, last_exit: null`, and the Tools pane
shows "5 runs" for a tool that has never executed a single command. Under §0.6 ("every count on
screen is measured by the code that shows it") `runs` measures invocations while being labelled a
run. The internal inconsistency — `runs: 5` with `median_ms: null` — is the tell, but only a reader
who knows to look for it. Either rename it (`calls`/`invocations`) or increment it where the
`executed_step` stat is pushed.

**Failure scenario B (identity).** `register()` carries the counter across a replacement:
`runs: replacing?.runs ?? 0` (line 299). Re-forging `hn_top` with different commands produces a new
content hash and requires a fresh human approval — the whole point of §13.5's identity-hash pitch to
Nahas — yet the new tool inherits the old one's run count and reports it under the new hash. The
stats cross exactly the identity boundary the hash exists to draw. `stats` (which drive `median_ms`
and `last_exit`) are correctly reset; only `runs` leaks through, so the two disagree after a
re-forge.

## Checked and clean (stated so the next reviewer can skip them)

- **The human-Enter gate holds.** Every path to the PTY is `client.sendInput`, and there are exactly
  three call sites: `Terminal.tsx:131` (xterm `onData` — real keystrokes), `Terminal.tsx:178`
  (Tab-insert, sends the command **without** `\r`, so it cannot execute), and `adapter.ts:257`
  (`command + '\r'`, reached only from `acceptProposal`). Both `acceptProposal` callers
  (`Terminal.tsx:174,186`) are inside the keydown handler, gated on `!running && lineBuf.empty`,
  with a second Enter required when `p.dangerous`. No agent-reachable path writes to the PTY.
- **Redaction choke point holds for status.** `terminal_status` gates `cwd` on `shareScreen()`
  (`register.ts:160`) and never returns `last_command` — I grepped: `last_command` reaches no
  agent-facing surface. `last_rokan` carries only `{ms, replayed, calls}`, never the answer text.
- **`allowedHosts` is a real, read property** of `@cloudflare/containers` (`container.d.ts:68`,
  used at `container.js:209`) — I initially suspected a dead field and it is not. The defect is the
  interception mode, not the property.
- **Forge hash collision is not a practical risk**: 12 hex = 48 bits, ~16.7M tools for a birthday
  collision, against a hard cap of 5 visible.
- **Trailer attribution** (my pass-3 P1) remains correct at `bridge.js:118`.

## Note on scope

Both findings are in the same class as the ones that have run through this repo all week: not
broken code, but a **control that stopped enforcing while its description kept asserting it**. The
P0 arrived as a side effect of a legitimate functional fix, and the comment written in the same
commit states the opposite of what the SDK does. Worth asking of the remaining fixes: when a
control is relaxed to make a demo work, what re-checks the sentence that describes it? Right now,
nothing does — `SECURITY.md:7` claims test coverage that `infra/sandbox/test/` does not contain.
