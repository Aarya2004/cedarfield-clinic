## P1

### 1. Without zsh shell integration, the first agent proposal wedges the terminal permanently.
`apps/web/src/lib/terminal/adapter.ts:85,90`

An in-flight proposal only finishes when **both** happen: an OSC 133;C `start` event flips
`phase` to `'running'` (line 85), *then* a `status` frame with `running:false` arrives (line 90).
Both come only from the zsh integration. With any other shell the bridge emits neither, so
`finish()` never runs, `inflight` is never cleared — and `acceptProposal` early-returns on
`if (inflight) return false` (line 172). **Every subsequent proposal is silently refused for the
life of the session,** and the agent's `terminal_wait` returns `still_waiting` forever.

Measured A/B, same probe, same command (`echo probe_marker; false`):

```
shell=/bin/bash  integration=false
  command output streamed : true
  OSC 133;C (start) seen  : false      <- phase never becomes "running"
  status frames received  : 0          <- finish() never called
  VERDICT: inflight stuck -> acceptProposal() returns false forever

shell=/bin/zsh   integration=true
  OSC 133;C (start) seen  : true
  status frames received  : 2   last: {running:false, last_exit_code:1, last_command_ms:0}
  VERDICT: proposal WOULD resolve
```

The demo Mac and the judge container are both zsh, so the golden path is safe. But `npx
rokan-terminal` invites anyone to run it, `--shell` is a documented flag, and bash is the default
login shell on most Linux boxes — including the "any machine / remote box" beat in PLAN §13.2.
`Panes.tsx:45` does honestly display "· no shell integration", so the user is *told* status is
unmeasured; they are not told the agent path is dead.

Fix: a fallback completion path when `hello.integration === false` — resolve on the next prompt
marker or a timeout, with `exit_code: null, ms: null, measured:false` (the honest values the schema
already models), and clear `inflight` unconditionally on `waitProposal` timeout.

### 2. Forged-tool execution rows never reach the bridge and are never countersigned.
`apps/web/src/lib/webmcp/forge.ts:447` · `apps/web/src/lib/ws/protocol.ts:24` · `session.ts:93`

The forge queue runner records each completed step as kind **`executed`**:

```ts
void this.deps.ledger.append('executed', { tool, invocation_id, step, exit_code, ms });
```

The forward gate only sends kinds in the shared allowlist:

```ts
if (CLIENT_LEDGER_KINDS.has(row.kind)) client.forwardLedger(row);
```

and that allowlist contains **`executed_step`**, not `executed`:

```
bridge accepts 'executed'      : false
bridge accepts 'executed_step' : true
producers of 'executed_step'   : none (grep, whole repo)
```

So the kind was renamed on the contract side and the only producer was never updated. Every
"forged tool ran, exit 0, N ms" row — **the row the hero shot ends on** — is silently dropped
before the bridge, gets no countersignature, and will show up in `rokan-terminal verify` as
un-countersigned. It is masked because the bridge writes its *own* `executed` rows from the OSC
markers, so `ledger.jsonl` looks populated, and because the page ledger renders the row correctly,
so the demo looks right.

No test covers it: the unit tests use a fake ledger, and the eval cases assert on page state, not on
what crossed the socket. Fix the producer to `executed_step` (or add `executed` to the allowlist —
but it collides with the bridge-owned kind, so renaming the producer is the safe direction) and add
one smoke assertion that a forged invocation produces a `client:executed_step` row.

### 3. `POST /api/session` executes for disallowed origins; CORS only hides the response.
`infra/sandbox/src/worker.ts:37-41,57`

`cors()` returns `{}` when the origin isn't allowed, but the handler runs anyway — it allocates the
Gate slot and starts a container. A plain cross-origin `POST` with no custom headers is a CORS
*simple request*: no preflight, so nothing stops it being sent. Any page a judge visits can burn
their `SESSIONS_PER_IP_PER_10MIN` (default **1**) quota, and the judge then gets
`429 … try again in N s` when they open the real URL. That is a cheap denial of the Gate D
"stranger opens it cold" beat.

Fix: if the origin is present and not allowed, return `403` before touching `gate.allow()`.

## P2

4. `worker.ts:102` — `/ws/:sid` calls `getSandbox()` for any well-formed sid with **no Gate check and
   no ownership check**, so unauthenticated requests can instantiate Sandbox DOs outside the rate
   limiter. The bridge token still blocks PTY access, so this is resource abuse, not takeover. I
   could not test against a live deploy (blocked on `wrangler login`) — verify when it deploys.
5. `worker.ts:93-99` — `DELETE /api/session/:sid` has no ownership check *and* calls `release(sid)` on
   the **caller's** Gate DO. A third party who learns a sid destroys the victim's sandbox while the
   victim's rate-limit row stays consumed — destroyed *and* locked out for 10 minutes.
6. `packages/bridge/src/mcp.js:108` — `destructiveHint: !t.annotations?.readOnlyHint` marks
   `terminal_propose` **destructive** over MCP, while WebMCP describes the same tool as
   `readOnlyHint:false` and inert. One registry, two protocols, two different safety claims — the
   drift "one registry" is meant to prevent, and it is in Nahas's exact lens.
7. `apps/web/src/components/Terminal.tsx:226` — `dir="auto"` on the ghost overlay. Bidi *control*
   chars are rejected by `validateProposedCommand`, but a command beginning with a strong-RTL
   *letter* (category Lo, not Cf) still flips render order, so displayed order ≠ executed order —
   the ghost-text spoofing class from ALIGNMENT §4.2. `dir="ltr"` is correct for a shell line.
8. `apps/web/src/lib/webmcp/ledger.ts:12` vs `ws/protocol.ts:24` — client `LedgerKind` permits
   `executed` (which the bridge drops) and omits `executed_step` (which it accepts). The two enums
   are not the same set; this is the root cause of finding 2 and will cause the next one too.
9. `apps/web/src/lib/ws/client.ts:164` — `this.pingTimer = setInterval(...)` on `hello` without
   clearing an existing timer; a duplicate `hello` on one socket leaks an interval and doubles the
   ping rate. One-line guard.
10. `apps/web/src/lib/ws/client.ts:251` — input typed during the `connecting` window is queued (≤100)
    and flushed on `hello`. The bridge can respawn the shell (`shell_restarted` is a real ledger
    kind), so those bytes can land in a *different* shell than the one the human was looking at when
    they typed them.
11. `packages/bridge/src/mcp.js:42` — `AgentLink` never reconnects. After a bridge restart the MCP
    server keeps advertising a stale tool list and every `call()` rejects with "not connected", with
    no recovery short of restarting the MCP client.

## Objection (process, one — carried from pass #1 and now demonstrated)

Pass #1 I argued the harness can pass steps the product cannot do. Finding 2 is the second instance
and a sharper one: **98 unit tests and 174 eval steps all pass while the ledger row the entire hero
shot rests on never leaves the tab.** Both layers are blind in the same way — the unit tests use a
fake ledger, the eval cases assert page state. Nothing asserts on what crossed the WebSocket.

Suggest one cheap addition before freeze, not a new layer: extend the existing real-PTY smoke with
an assertion that a *forged tool invocation* yields a `client:executed_step` row carrying a bridge
countersignature. That is the one claim the submission text makes that nothing currently checks end
to end, and it would have caught this in the commit that renamed the kind.
