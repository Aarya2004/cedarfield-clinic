## P0

### 1. The bridge ledger's HMAC does not cover nested objects. Tamper-evidence is bypassable.
`packages/bridge/src/ledger.js:16`

```js
function canonical(obj) { return JSON.stringify(obj, Object.keys(obj).sort()); }
```

`JSON.stringify`'s second argument, when an array, is a **key allowlist applied recursively** — not a
sorter for the top level only. `Object.keys(obj)` is top-level keys, so **every key of every nested
object is filtered out of the digest.**

Proven (`scratchpad/probe2.mjs`, isolated, N=1):

```
stored row   : {"seq":1,...,"params":[{"name":"n","example":"5"}],"sig":"0f78f3da…"}
digest input : {"hash":"abc123","kind":"forged","name":"hn_top","params":[{"name":"n"}],…}
                                                             ^^^^^^^^^^^^^^ "example" silently dropped

top-level tamper (hash abc123 -> DEADBEEF)   -> verifyLedger {"ok":false,"firstBad":"seq 1: bad sig"}   (detected)
nested tamper (params[0].example 5 -> PWNED) -> verifyLedger {"ok":true,"firstBad":null}                (UNDETECTED)
```

(`name` survives only by coincidence — it collides with a top-level key.)

Why this is P0 rather than a nit: FORGE-PLAN §4.9 writes `forged {name, hash, kind, commands, params,
previous_hash}` through this exact path, and §6 sells the content hash + ledger as the answer to
tool-framing attacks. An attacker (or an honest bug) can rewrite a forged tool's param descriptions
and examples in the ledger and `verifyLedger()` still returns `ok:true`. `commands` is safe (array of
strings), `params` is not (array of objects).

Worse: `smoke.mjs:94` tampers `exit_code`, a top-level scalar, so **the 14/14 smoke gives false
confidence** — it tests the case that works.

Fix: a real recursive canonicaliser (sort keys at every depth, then plain `JSON.stringify`). Add a
smoke check that tampers a *nested* field.

### 2. The client ledger exports its own HMAC key next to the rows.
`apps/web/src/lib/webmcp/ledger.ts:104,109`

```ts
export(): LedgerExport { return { session, key_hex: this.keyHex, rows: this.rows }; }
private persist() { window.localStorage.setItem(STORAGE_KEY, JSON.stringify(this.export())); }
```

The export — and the localStorage mirror — carries `key_hex` beside the rows it authenticates.
Anyone who can edit the rows can re-sign them. `verifyExport()` then returns `ok:true` on forged
data. As shipped, the client chain proves ordering and detects accidental corruption; it does not
detect tampering, which is what §4 and the draft submission text claim.

**The honest, and much stronger, fix is already half-built.** The bridge already returns
`{type:'ledger_ack', seq, sig}` for every client row, signed with a key that lives in
`~/.rokan-terminal/keys/` (0600) and **that the page never sees**. That countersignature is the only
signature in the system whose key the signer-of-record does not control — it is the real asset. Store
the ack `sig` on the client row and verify against the bridge. Then either drop `key_hex` from the
export or state plainly what the page-local chain does and doesn't prove.

Related framing note for the submission text: on the bridge side the key sits in the same directory,
same uid, as `ledger.jsonl`. Against a local attacker that is not tamper-*proof* either. Say
"tamper-evident: ordering and integrity of the local log, countersigned by the bridge" — that is
true, defensible, and still earns the Nahas point. Do not write "tamper-proof".

## P1

### 3. `parsePairingHash` accepts any WebSocket host — crafted link = keylogger.
`apps/web/src/lib/ws/protocol.ts:79`

```ts
if (!/^wss?:\/\//.test(ws)) return null;
if (!/^[a-f0-9]{16,64}$/.test(token)) return null;
```

Scheme and token *shape* are checked; the **host is not**. A link like
`https://rokan-terminal.vercel.app/#ws=wss://evil.example/&t=<any 32 hex>` passes validation. The WS
client (not written yet — Aarya's lane) would then connect to the attacker, render attacker-controlled
`data` frames into xterm, and send **every keystroke** to them. That defeats "the keyboard is the
boundary" completely, and it is a one-link phish.

Catch it before the client exists. Allowlist the host: `127.0.0.1` / `localhost` / `*.trycloudflare.com`
(+ the judge-mode Worker origin), else refuse with a visible message.

### 4. The pairing token lives in `location.hash` forever, and there is no CSP.
`next.config.ts` is the empty scaffold; `bin/rokan-terminal.js:62` puts the token in the fragment.

Two consequences:
- Any third-party script on the page can read `location.hash`. That is precisely the
  arXiv 2606.06387 threat model the entry cites. Today there is no CSP to stop one.
- The token stays in the address bar. **It will be on camera in the demo video and in every
  screenshot in `docs/evidence/`.** Check the Gate A screenshot before the repo goes public.

Fix (cheap, both): `history.replaceState(null,'', location.pathname)` immediately after parsing the
hash; add a strict `Content-Security-Policy` via `next.config.ts` `headers()`. The CSP is also a free
judge point — it is the correct answer to the paper they're citing.

### 5. `isDangerous()` is never called on the proposal path.
`apps/web/src/lib/webmcp/schemas.ts:77` — only caller is `forge-spec.ts`.

`register.ts` `terminal_propose` runs `validateProposedCommand` only. PLAN §4 and test T2.2 require
`rm -rf /` to render with a red banner and a second confirmation. Right now it ghost-types like any
other command. This is a written test-protocol item that currently fails, on the security beat.

### 6. CI never runs the tests.
`.github/workflows/ci.yml` runs web typecheck/lint/build + bridge `check`. It does **not** run
`pnpm --filter web test` (the 12 redaction tests guarding the security choke point) or the evals.
Redaction can silently regress on `main`. Add one line; `smoke` can stay out (needs a PTY).

### 7. README describes directories that are empty.
`infra/` and `vendor/` contain nothing; README presents `infra/sandbox` and the vendored wheels as if
they exist. Judges read the README first and §0.6 is "say the true thing". Mark them planned until
they land.

### 8. Enter only works if the human has clicked the terminal first.
`apps/web/src/components/TerminalTools.tsx:62` — `onKeyDown` on `<section tabIndex={0}>`, no
`autoFocus`, no document-level fallback.

The harness passes because `webmcp-cdp.mjs:67` **explicitly focuses that element** before dispatching
the key. A real human who opens the page, asks ChatGPT to propose `ls`, and presses Enter gets
nothing. This is exactly the shape of the April 23 failure: green tests, dead demo. Autofocus the
prompt on mount and add a `document`-level handler.

## P2

9. **Contract drift, PLAN §3 vs `schemas.ts`.** PLAN row 4 and test T2.4 say `terminal_wait` times out
   at **120 s**; `WAIT_DEFAULT_MS = 45_000`. PLAN's row 2/4 return shapes omit `redactions`,
   `truncated`, `reason`, and `still_waiting`, all of which ship. PLAN §3 is what a judge reads.
10. **`terminal_status` returns `cwd` ungated and unredacted** (`register.ts:130`). Everything else
    buffer-derived goes through `redactForAgent`; this bypasses both the Share-screen gate and the
    choke point, and leaks home-dir and project names (`/Users/aravkekane/dev/<unreleased>`) with
    sharing OFF. Either gate it or truncate to a basename.
11. **The two ledgers canonicalise differently** — client nests under `fields` with fixed key order,
    bridge spreads flat and sorts. The docs say the same row lands in both; their signatures can
    never be cross-checked. Pick one canonical form.
12. **`ledger.append` poisons its own promise chain.** `this.chain = this.chain.then(...)` — one
    rejection makes every later append reject forever, and every caller is `void`-ed, so it fails
    silently. Realistic trigger: `crypto.subtle` is undefined on a non-localhost **http://** origin,
    e.g. testing from `http://192.168.x.x:3311` on a phone or Aarya's machine. Page looks fine, ledger
    stays empty. Add a `.catch()` that keeps the chain alive.
13. **Concurrent proposals hang.** Nothing stops two `terminal_propose` calls; the key handler only
    resolves the newest, so the older one never resolves and its `terminal_wait` returns
    `still_waiting` forever. FORGE-PLAN §4.7 assumes "one at a time by construction" — that guard
    doesn't exist yet on the fixed tool.
14. **OSC parser loses a marker split across chunks at exactly the ESC byte.** `shell-integration.js:96`
    sets `carry = ''` when no `ESC]` is found, discarding a trailing lone `\x1b`. Rare; cheap to fix by
    retaining a trailing ESC.
15. `mkdtempSync` ZDOTDIR (`shell-integration.js:25`) is never cleaned up — one temp dir per bridge run.
16. Idle timeout closes the socket but leaves the process **and the public tunnel** alive
    indefinitely (`bridge.js:101`). After a demo, walking away leaves a live tunnel.
17. `evals/run-all.mjs:6` uses `new URL(...).pathname` instead of `fileURLToPath` (breaks on spaces);
    harness `send()` has no timeout, so a stalled Chrome hangs the run forever.
18. `fitBudget` (`register.ts:46`) re-`JSON.stringify`s the whole array per dropped line (O(n²) at 200
    lines); its `kept.length !== lines.length` term is dead — `map` preserves length.

## Not findings (checked, and fine)

- The ANSI/OSC strip regex in `redact.ts:64` is correct, including the OSC branch and C0/C1 stripping.
  I read the raw bytes; it is not the naive version I expected.
- PEM handling fails closed: an unterminated BEGIN block drops all subsequent lines.
- `terminal_wait`'s tail *is* correctly gated on Share-screen and passed through the same
  `redactForAgent` choke point — the hole Aarya's Claude flagged in ALIGNMENT is genuinely closed.
- Token comparison is length-checked before `timingSafeEqual` (`bridge.js:114`), which is the right
  order — `timingSafeEqual` throws on length mismatch.
- Feature detection of `document.modelContext ?? navigator.modelContext` is correct and the page
  degrades cleanly without WebMCP.

## Objection (one, on ordering — founders decide)

FORGE-PLAN §16 makes "test every baby step" non-negotiable and §7 makes headless evidence the Gate C
bar. Finding 8 shows the harness can pass a step **the product cannot do** because the harness
arranges preconditions a human doesn't have (focus). Suggest one rule for the remaining harness cases:
*a step that needs setup the human wouldn't perform must be written as the human performs it, or the
case must be marked as not-demo-evidence.* Otherwise the evals folder — which Gao reads — will
accumulate green cases that don't imply a working demo.
